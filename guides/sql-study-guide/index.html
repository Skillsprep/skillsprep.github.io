SQL Study Guide: Queries You Should Master

13 min read 20 Questions Published Aug 15, 2026 Reviewed Oct 18, 2026

Unofficial study resource. Written independently of any exam provider, employer or software vendor.

SQL interviews and skills tests often ask you to read and reason about queries more than to write them from scratch. JOIN types, aggregation, and the difference between WHERE and HAVING come up constantly.

Must-know query patterns

  • JOIN types — INNER, LEFT, RIGHT, FULL OUTER, and CROSS — and which rows survive each
  • Aggregation — GROUP BY with COUNT, SUM, AVG, MAX, MIN
  • WHERE vs HAVING — filter rows before grouping vs filter groups after
  • Subqueries — in WHERE, FROM, and SELECT
  • Window functions — ROW_NUMBER(), RANK(), OVER (PARTITION BY ...)
  • Indexes — what they speed up and their cost on writes

WHERE vs HAVING — the classic trap

SELECT department, AVG(salary)
FROM employees
WHERE status = 'active'      -- filters ROWS first
GROUP BY department
HAVING AVG(salary) > 50000;  -- filters GROUPS after

You cannot use an aggregate in WHERE — the aggregate doesn't exist yet when WHERE runs. Interviewers love testing this.

Memory trick WHERE = filter rows → then GROUP → then HAVING = filter groups.

JOIN types at a glance

Given tables customers and orders:

  • INNER JOIN — only customers who have orders
  • LEFT JOIN — all customers, with NULLs where no order exists (find customers who never ordered: WHERE o.id IS NULL)
  • FULL OUTER — everyone from both sides, NULLs filling gaps (not supported in MySQL)

A common question asks "return all rows from one table whether or not there's a match" — the answer is LEFT (or RIGHT) JOIN.

How a query is really evaluated

You write SELECT first, but the database logically handles it nearly last. Knowing the logical order explains most "why can't I use that here?" errors. The order is: FROM (and JOINs) builds the working rows, WHERE filters rows, GROUP BY forms groups, HAVING filters groups, SELECT computes the output columns, ORDER BY sorts, and finally the row limit is applied. Optimisers may physically execute things differently, but the result must behave as if this order were followed.

Three practical consequences follow:

  • A column alias defined in SELECT usually cannot be used in WHERE, because WHERE ran earlier. It can be used in ORDER BY, which runs afterwards. Some dialects are more lenient in GROUP BY or HAVING, so do not rely on that when writing portable SQL.
  • Aggregates cannot appear in WHERE, since groups do not exist yet.
  • Every non-aggregated column in SELECT must appear in GROUP BY (or be functionally dependent on it, which only some databases accept).

Limiting rows is where dialects differ most:

SyntaxWhere you will meet it

-- Three highest-paid employees, standard form
SELECT name, salary

ORDER BY salary DESC

Always pair a limit with ORDER BY Without it, "the first 3 rows" is whatever the engine happens to return, and the answer can change between runs.

NULL and three-valued logic

NULL means "unknown", not zero and not an empty string. Comparisons with an unknown value give an unknown result, so SQL has three truth values: TRUE, FALSE and UNKNOWN. A WHERE clause keeps only rows where the condition is TRUE, so UNKNOWN rows are dropped just like FALSE ones.

ExpressionResult
NULL = NULLUNKNOWN (not TRUE)
5 <> NULLUNKNOWN
NULL IS NULLTRUE
TRUE AND UNKNOWNUNKNOWN
TRUE OR UNKNOWNTRUE
NOT UNKNOWNUNKNOWN

That last row is why NOT IN is dangerous. Suppose you want customers who have never ordered:

-- Looks right, but returns NOTHING if any orders.customer_id is NULL
SELECT name FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders);

-- Safe version
SELECT c.name FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.id
);

Why does the first fail? id NOT IN (1, 3, NULL) expands to id <> 1 AND id <> 3 AND id <> NULL. For id = 2 the last test is UNKNOWN, so the whole expression is UNKNOWN and the row is discarded. One NULL in the list empties the result. NOT EXISTS, or a LEFT JOIN with WHERE o.id IS NULL, avoids the problem.

Other NULL habits worth having: aggregates such as SUM, AVG and COUNT(column) ignore NULLs; COALESCE(x, 0) returns the first non-NULL argument; and GROUP BY treats all NULLs as one group even though they are not "equal".

Joins by hand, and the mistakes that follow

The fastest way to understand joins is to run them on paper. Take two tiny tables.

customers.idname
1Asha
2Ben
3Chen
orders.idcustomer_idamount
101150
102130
103320

An INNER JOIN on customers.id = orders.customer_id yields three rows: Asha twice, Chen once. Ben vanishes because he has no match. A LEFT JOIN yields four rows: the same three plus Ben with NULL in every orders column. A customer with two orders appears twice, because a join produces one output row per matching pair.

COUNT(*) versus COUNT(column). Using the LEFT JOIN result, count orders per customer:

SELECT c.name, COUNT(*) AS wrong, COUNT(o.id) AS right
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.name;
namewrongright
Asha22
Ben10
Chen11

COUNT(*) counts rows, and Ben's NULL-padded row is still a row. COUNT(o.id) counts only non-NULL values, so Ben correctly gets 0.

Join fan-out. If each order also has several rows in an order_items table and you join all three tables, each order row is repeated once per item. Then SUM(o.amount) counts the same amount several times. Fix it by aggregating the many-side first in a subquery or CTE, then joining the already-summarised result, or by summing at the item level.

Filtering a LEFT JOIN. Putting a condition on the right table in WHERE (for example WHERE o.amount > 25) removes the NULL-padded rows and silently turns the query into an inner join. If you want to keep unmatched left rows, put the condition in the ON clause instead.

Window functions and CTEs

A window function computes a value for each row using a related set of rows, without collapsing them the way GROUP BY does. The shape is function() OVER (PARTITION BY ... ORDER BY ...). PARTITION BY splits rows into independent groups; ORDER BY defines the sequence inside each one.

The three ranking functions differ only in how they treat ties. With salaries 90, 90, 80:

salaryROW_NUMBERRANKDENSE_RANK
90111
90211
80332

ROW_NUMBER never repeats (tied rows are ordered arbitrarily unless you add a tie-breaker), RANK repeats and then skips, and DENSE_RANK repeats without skipping. Pick based on whether "second highest" should mean the second row or the second distinct value.

A running total uses an aggregate as a window function:

SELECT order_date, amount,
       SUM(amount) OVER (
         ORDER BY order_date
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM orders;

Spelling out the ROWS frame matters. When a frame is omitted, the default usually treats rows with equal ORDER BY values as peers, so two orders on the same date would show the same running total.

Window functions cannot be used directly in WHERE, because they are evaluated after it. The standard workaround is a CTE (common table expression), a named temporary result defined with WITH:

WITH ranked AS (
  SELECT name, department, salary,
         ROW_NUMBER() OVER (
           PARTITION BY department ORDER BY salary DESC
         ) AS rn
  FROM employees
)
SELECT name, department, salary
FROM ranked
WHERE rn <= 2;   -- top 2 per department

CTEs make long queries readable by naming each step, and several can be chained with commas. Treat them mainly as a readability tool; whether a CTE is cached or inlined depends on the database.

Indexes, practice plan and glossary

Indexes, conceptually. An index is a separate sorted structure (commonly a B-tree) that lets the database find rows by a column's value without reading the whole table, like a book's index versus reading every page. It helps with WHERE equality and range filters, join columns, and sometimes ORDER BY. The costs are extra storage and slower INSERT, UPDATE and DELETE, since each index must be maintained. Indexes help less when a query needs most of the table anyway, and a function wrapped around the column (such as WHERE UPPER(name) = 'ASHA') can stop a plain index being used. In a composite index on (a, b), a query filtering only on b generally cannot use it efficiently, because the sort is by a first.

Interview-style reasoning. When asked to "find the second-highest salary", state your assumptions out loud: do ties count once (DENSE_RANK) or separately (ROW_NUMBER)? What should happen if there is no second value? Explaining the choice earns more than a memorised snippet.

How to practise.

  1. Create the customers and orders tables above in any free engine (SQLite is enough) and predict each result on paper before running it.
  2. Rewrite one NOT IN query three ways: NOT EXISTS, LEFT JOIN with IS NULL, and NOT IN. Then insert a NULL and compare.
  3. Take any GROUP BY query and recompute it with a window function, noting which rows survive.
  4. Run your engine's explain command (EXPLAIN, or its equivalent) before and after adding an index and read how the plan changes.

Practical learning exercises

  • Exercise 1 (Joins): Write a query to join a Customers table and an Orders table. Return all customers, including those who haven't placed an order (using a LEFT JOIN), and handle NULLs with the COALESCE function.
  • Exercise 2 (Aggregations): Group an Employees table by Department and use aggregate functions to find the average salary and the total number of employees per department. Filter out departments with fewer than 5 employees using the HAVING clause.
  • Exercise 3 (Window Functions): Write a query using ROW_NUMBER() OVER(PARTITION BY department ORDER BY salary DESC) to find the highest-paid employee in each department.

Practice questions

Question 1 of 20Aggregation

You want to list only departments whose average salary exceeds 60,000. Which clause filters this correctly?

Why: Aggregates are computed during grouping, so they can only be filtered with HAVING after GROUP BY. WHERE runs before grouping and can't reference aggregates.
Question 2 of 20JOINs

Which join returns ALL rows from the left table, with NULLs where there is no match on the right?

Why: LEFT JOIN preserves every row from the left side regardless of matches. INNER drops non-matching rows from both sides; CROSS returns the Cartesian product.
Question 3 of 20Window Functions

To number rows within each department by salary (highest first), you would use:

Why: PARTITION BY department restarts numbering per department, and ORDER BY salary DESC puts the highest first. Plain GROUP BY would collapse rows and couldn't produce per-row numbers.
Question 4 of 20Aggregation

Which clause is used to filter the results of aggregate functions?

Why: The HAVING clause was added to SQL because the WHERE keyword cannot be used with aggregate functions.
Question 5 of 20Subqueries

What is a correlated subquery?

Why: A correlated subquery evaluates once for each row processed by the outer query, as it references columns from the outer query.
Question 6 of 20Filtering

Which clause is used to filter the results of an aggregate function like SUM or COUNT?

Why: The HAVING clause filters groups after aggregation, whereas WHERE filters rows before aggregation.
Question 7 of 20Joins

What does an INNER JOIN return?

Why: INNER JOIN strictly requires a match in both joined tables.
Question 8 of 20Nulls

How do you check if a column value is NULL?

Why: NULL cannot be evaluated with equality operators; you must use the `IS NULL` operator.
Question 9 of 20Sorting

Which keyword sorts the result set in descending order?

Why: DESC specifies descending order in an ORDER BY clause.
Question 10 of 20Functions

Which function returns the number of non-null values in a column?

Why: `COUNT(column)` counts non-null entries, while `COUNT(*)` counts all rows.
Question 11 of 20Set Operators

What is the difference between UNION and UNION ALL?

Why: UNION performs a distinct operation (which is slower), while UNION ALL simply appends result sets.
Question 12 of 20Wildcards

In the LIKE operator, what does the `%` symbol represent?

Why: `%` is a wildcard for any sequence of characters.
Question 13 of 20Data Manipulation

Which statement is used to modify existing records in a table?

Why: UPDATE changes data inside a table, while ALTER changes the table structure.
Question 14 of 20Constraints

What does a PRIMARY KEY constraint do?

Why: A primary key enforces entity integrity (unique and not null).
Question 15 of 20Window Functions

Which clause is essential when writing a window function?

Why: The OVER clause defines the window (set of rows) the function operates on.
Question 16 of 20Subqueries

Can a subquery return multiple columns?

Why: When used in the FROM clause, a subquery acts as a temporary table and can have multiple columns.
Question 17 of 20Transactions

What command undoes a transaction if an error occurs?

Why: ROLLBACK reverts the database to the state it was in before the transaction began.
Question 18 of 20Aliases

How do you assign an alias to a column in a query?

Why: The AS keyword (or just a space) is used to create a temporary alias for a column or table.
Question 19 of 20Data Types

Which data type is best for storing a fixed-length string, like a 2-letter state code?

Why: CHAR is used for fixed-length strings and is often more efficient for that purpose.
Question 20 of 20Optimization

What database object improves the speed of data retrieval operations?

Why: Indexes work like a book's index, allowing the database to find rows quickly without scanning the whole table.

Preparation checklist

  • Practice the 5 JOIN types and the anti-join pattern (LEFT JOIN + IS NULL)
  • Memorize the WHERE → GROUP BY → HAVING → ORDER BY execution order
  • Know basic index trade-offs: faster reads, slower writes, extra storage
  • For window functions, understand what PARTITION BY changes compared with a plain ORDER BY
