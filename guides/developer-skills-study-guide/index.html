Developer Fundamentals: HTTP, APIs, Debugging and Testing

13 min read 20 Questions Published Nov 22, 2026 Reviewed Nov 22, 2026

Interviews for junior developers test more than a language: how you use the command line, what an API call actually sends, how you find a bug, how you test, and whether you protect secrets. This guide covers those skills with short, runnable examples. Every code block is a complete script that was run before publishing, and each is labelled by its first line. For language and tooling basics, see the Git, JavaScript and Python guides. This is an unofficial study aid.

What you will learn

By the end you should be able to:

  • Use pipes, redirects, exit codes and environment variables in a shell
  • Choose HTTP methods and status codes correctly, and say which methods are safe and idempotent
  • Read and write valid JSON, and handle malformed input
  • Reproduce, isolate and fix bugs with a repeatable process
  • Write unit tests that cover normal, edge and error cases
  • Apply basic security habits: parameterized queries, server-side validation and secret handling

The command line

A shell lets you chain small programs. A pipe (|) sends one command's output into the next, > redirects output to a file, every command ends with an exit code (0 means success, non-zero means failure), and environment variables pass settings to programs.

# shell
mkdir -p demo && cd demo
printf 'apple\nbanana\napple\n' > fruit.txt
sort fruit.txt | uniq -c        # counts each distinct line
grep -c apple fruit.txt         # 2
grep -q cherry fruit.txt; echo "exit code: $?"   # exit code: 1
export GREETING=hello
sh -c 'echo "$GREETING"'        # hello

The $? variable holds the previous command's exit code, which is how scripts and CI systems decide whether a step succeeded.

HTTP: methods and status codes

A request has a method, a URL, headers and sometimes a body; a response has a status code, headers and usually a body. MDN lists these properties:

MethodPurposeSafeIdempotent
GETRetrieve a representation of a resourceYesYes
HEADSame as GET without the response bodyYesYes
POSTSubmit an entity, often causing a change or side effectsNoNo
PUTReplace the target resource with the request contentNoYes
PATCHApply a partial modificationNoNo
DELETEDelete the resourceNoYes
ClassMeaningCommon codes
2xxSuccess200 OK, 201 Created, 204 No Content
3xxRedirection301 Moved Permanently, 304 Not Modified
4xxClient error400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests
5xxServer error500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable
401 versus 403 Although the standard says "unauthorized", 401 semantically means unauthenticated: the client must authenticate. 403 means the server knows who the client is and still refuses. A server may return 404 instead of 403 to hide that a resource exists.

REST APIs and JSON

A REST-style API exposes resources at URLs and uses methods for the action: GET /items lists, POST /items creates. JSON is the usual body format. JSON requires double-quoted property names and strings, forbids trailing commas and comments, and has no undefined, NaN or Infinity.

// node
try { JSON.parse("{'a': 1}"); } catch (e) { console.log(e.name); }            // SyntaxError
console.log(JSON.parse('{"a": [1, 2, null]}').a.length);                      // 3
console.log(JSON.stringify({ a: undefined, b: 1, c: function () {} }));       // {"b":1}

The script below runs a tiny API on your own machine and calls it. It returns 201 for a created item, 400 for malformed JSON or a missing field, 200 for the list, and 404 for an unknown path.

// node
const http = require("node:http");
const items = [];
const server = http.createServer((req, res) => {
  const send = (code, body) => {
    res.writeHead(code, { "Content-Type": "application/json" });
    res.end(JSON.stringify(body));
  };
  if (req.method === "GET" && req.url === "/items") return send(200, items);
  if (req.method === "POST" && req.url === "/items") {
    let data = "";
    req.on("data", (chunk) => (data += chunk));
    req.on("end", () => {
      let item;
      try { item = JSON.parse(data); } catch (e) { return send(400, { error: "invalid JSON" }); }
      if (typeof item.name !== "string" || item.name === "") return send(400, { error: "name is required" });
      items.push(item);
      send(201, item);
    });
    return;
  }
  send(404, { error: "not found" });
});
server.listen(0, async () => {
  const base = "http://127.0.0.1:" + server.address().port;
  const post = (body) => fetch(base + "/items", { method: "POST", headers: { "Content-Type": "application/json" }, body: body });
  let r = await post(JSON.stringify({ name: "pen" }));
  console.log(r.status);                                  // 201
  r = await post("{bad json}");
  console.log(r.status);                                  // 400
  r = await post(JSON.stringify({}));
  console.log(r.status);                                  // 400
  r = await fetch(base + "/items");
  console.log(r.status, JSON.stringify(await r.json()));  // 200 [{"name":"pen"}]
  r = await fetch(base + "/nope");
  console.log(r.status);                                  // 404
  server.close();
});

Note the order of checks: parse the body (400 if malformed), then validate the fields (400 if wrong shape), then act. Valid JSON can still have the wrong shape.

Debugging

StepWhat to do
1. ReproduceMake the bug happen on demand, then shrink the input to the smallest failing case
2. Read the errorIn a Python traceback, read the last line first (the exception), then the frames above it to see where it came from
3. Hypothesise and testChange one thing at a time and predict the result before you run it
4. Narrow by halvingBisect versions, inputs or code until the first bad point is found
5. Fix and guardFix the cause, then add a test that fails without the fix

Halving is fast. This function finds the first bad version among 100 with 7 checks, the same idea that git bisect uses (see the Git guide).

# python
def first_bad(versions, is_bad):
    lo, hi = 0, len(versions) - 1
    checks = 0
    while lo < hi:
        mid = (lo + hi) // 2
        checks += 1
        if is_bad(versions[mid]):
            hi = mid
        else:
            lo = mid + 1
    return versions[lo], checks

print(first_bad(list(range(1, 101)), lambda v: v >= 37))   # (37, 7)

Logging beats scattered print statements because it has levels and formatting, and you can change the verbosity without editing code. Do not log passwords, keys or personal data.

# python
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
log = logging.getLogger("orders")

def total(prices):
    log.info("summing %d prices", len(prices))
    if not prices:
        log.warning("empty order")
    return sum(prices)

print(total([]))    # logs INFO and WARNING lines, then prints 0

Testing

The Python docs describe a test case as the individual unit of testing: it checks for a specific response to a particular set of inputs. A good test checks one behaviour, has a clear name, and follows arrange, act, assert. Cover the normal case, edges such as empty input and boundaries, and error paths.

# python
import unittest

def slugify(text):
    return "-".join(text.lower().split())

class SlugifyTests(unittest.TestCase):
    def test_basic(self):
        self.assertEqual(slugify("Hello World"), "hello-world")

    def test_extra_spaces(self):
        self.assertEqual(slugify("  a   b "), "a-b")

    def test_empty(self):
        self.assertEqual(slugify(""), "")

    def test_none_is_rejected(self):
        with self.assertRaises(AttributeError):
            slugify(None)

if __name__ == "__main__":
    unittest.main()

Run tests with python -m unittest. assertRaises passes only when the named exception is raised. setUp runs immediately before each test method, so tests do not share state.

Unit versus integration. A unit test checks a small piece in isolation and runs quickly. An integration test checks that parts work together, such as your code and a database. Use a fake for anything slow or unpredictable, such as the network or the clock:

# python
class FakeClock:
    def __init__(self, now):
        self.now = now

    def __call__(self):
        return self.now

def is_expired(expires_at, clock):
    return clock() >= expires_at

assert is_expired(100, FakeClock(150))
assert not is_expired(100, FakeClock(50))
print("ok")

Code review and reading documentation

  • Keep changes small. A small pull request is easier to review, test and revert.
  • Review for behaviour first: does it do what the description says, are edge and error cases handled, is there a test, and is anything secret or personal logged or committed? Style comes after.
  • Give specific, kind feedback that explains why, and separate must-fix issues from suggestions.
  • Read the error message in full before searching, then go to the official documentation for the exact behaviour. Docs change between versions, so check the version you use.

Security basics

OWASP, a widely used web security reference, describes its Top 10 as the reference standard for the most critical web application security risks. Three habits prevent a large share of beginner mistakes.

1. Use parameterized queries. OWASP's preferred defence against SQL injection keeps the SQL structure separate from data values. Concatenating untrusted values into the query defeats this protection:

# python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("create table users (name text, secret text)")
con.execute("insert into users values ('ann', 's1'), ('bob', 's2')")

name = "x' OR '1'='1"      # hostile input
unsafe = con.execute("select name from users where name = '" + name + "'").fetchall()
safe = con.execute("select name from users where name = ?", (name,)).fetchall()
print(unsafe)   # [('ann',), ('bob',)]   the input changed the query
print(safe)     # []                     the input was treated as data

2. Validate on the server. OWASP says to validate on the server even when the browser checks the same fields: client-side validation can be bypassed, so use it for immediate feedback. Define what the application accepts and reject everything else, instead of trying to recognise every malicious string.

3. Handle secrets carefully. Never hardcode API keys or passwords in source code or commit them. Read them from the environment (or a secrets manager), give each the minimum privileges it needs, and rotate any that may have been exposed, because removing a file in a later commit does not remove it from history.

# python
import os

api_key = os.environ.get("API_KEY")
if api_key is None:
    print("API_KEY is not set")   # fail clearly instead of using a hardcoded default

Practical learning exercises

  • Exercise 1 (shell). Given a file of fruit names, find the most common one. Solution: 
    # shell
printf 'apple\nbanana\napple\n' | sort | uniq -c | sort -rn | head -1    # 2 apple
  • Exercise 2 (status codes). Pick a code for each: a new item was created (201), the caller sent no credentials (401), a logged-in user lacks permission (403), the item does not exist (404), the caller is being rate limited (429), the service is down for maintenance (503).
  • Exercise 3 (JSON). Fix {'name': 'pen', 'tags': ['a', 'b',],}. Solution: use double quotes and remove both trailing commas. 
    // node
try { JSON.parse("{'name': 'pen', 'tags': ['a', 'b',],}"); } catch (e) { console.log("original:", e.name); }
console.log(JSON.parse('{"name": "pen", "tags": ["a", "b"]}').tags.length);   // 2
  • Exercise 4 (tests). Write tests for clamp(n, lo, hi) covering inside, below, above and the two boundaries. Solution: 
    # python
import unittest

def clamp(n, lo, hi):
    return max(lo, min(n, hi))

class ClampTests(unittest.TestCase):
    def test_inside(self):
        self.assertEqual(clamp(5, 0, 10), 5)

    def test_below(self):
        self.assertEqual(clamp(-3, 0, 10), 0)

    def test_above(self):
        self.assertEqual(clamp(42, 0, 10), 10)

    def test_boundaries(self):
        self.assertEqual(clamp(0, 0, 10), 0)
        self.assertEqual(clamp(10, 0, 10), 10)

unittest.main()
  • Exercise 5 (security). Rewrite "select name from users where name = '" + name + "'" safely. Solution: pass the value as a parameter, as in the safe query in the security section: con.execute("select name from users where name = ?", (name,)).

Interview questions

Try answering aloud before you open each one.

What does it mean for an HTTP method to be safe or idempotent?

A safe method is meant only to retrieve data, such as GET and HEAD. An idempotent method leaves the server in the same state however many times you repeat the request, such as GET, PUT and DELETE. POST and PATCH are neither, which is why retrying a POST can create duplicates.

What is the difference between PUT and POST?

PUT replaces the target resource with the request content and is idempotent. POST submits an entity to a resource, often causing a state change or side effects, and is not idempotent.

Explain 401 versus 403.

401 means unauthenticated: the client has not proved who it is. 403 means the server knows who the client is and refuses access anyway. A server may return 404 instead of 403 to hide that a resource exists.

What do the status code classes mean?

1xx informational, 2xx success, 3xx redirection, 4xx client error and 5xx server error. For example 201 means created, 304 means not modified (use the cached copy), 429 means too many requests, and 503 means temporarily unavailable.

What makes a document valid JSON?

Double-quoted property names and strings, no trailing commas, no comments, and only objects, arrays, numbers, strings, booleans and null as values. NaN, Infinity and undefined are unsupported, and numbers cannot have leading zeros.

How do you handle malformed JSON from a client?

Wrap parsing in a try/catch, since JSON.parse throws a SyntaxError on bad input, and return 400 Bad Request with a clear message. Then validate the parsed fields, because valid JSON can still have the wrong shape.

How do you debug a problem you cannot yet explain?

Reproduce it reliably, shrink the input to the smallest case that fails, and form a hypothesis you can test. Narrow the cause by halving the search space, such as bisecting versions or commenting out half the code, and add logging at the boundaries.

Logging or print statements?

Prints are fine for a quick look, but logging gives levels such as INFO and WARNING, formatting, and the ability to change verbosity without editing code. Do not log secrets or personal data.

What makes a good unit test?

It checks one behaviour, has a clear name, and follows arrange, act, assert. It covers normal inputs, edge cases such as empty values and boundaries, and error paths. It does not depend on the network, the clock or test order, so use a fake where needed.

Unit test versus integration test?

A unit test checks a small piece in isolation, usually fast. An integration test checks that several parts work together, such as your code with a database or an API. You need both, with more of the fast ones.

What is SQL injection and how do you prevent it?

Untrusted data becoming part of the SQL syntax and changing the query's logic. Prevent it with parameterized queries, which keep the SQL structure separate from the data values, rather than concatenating strings.

How should you handle API keys and passwords?

Never hardcode them in source code or commit them. Supply them through environment variables or a secrets manager, give each the minimum privileges it needs, and rotate any that may have been exposed.

Practice questions

Question 1 of 20HTTP

Which statement about the GET method matches MDN?

Why: MDN says GET requests a representation of a resource and should only retrieve data. GET, HEAD are safe, idempotent and cacheable.
Question 2 of 20HTTP

Which of these methods is NOT idempotent according to MDN?

Why: Repeating a PUT or DELETE leaves the server in the same state. POST often causes a change in state or side effects, so repeating it can create duplicates.
Question 3 of 20HTTP

What is the difference between PUT and PATCH?

Why: MDN: PUT replaces all current representations of the target resource with the request content, while PATCH applies partial modifications.
Question 4 of 20Status codes

A POST successfully creates a new resource. Which status code is typically returned?

Why: 201 means the request succeeded and a new resource was created, typically after POST requests or some PUT requests.
Question 5 of 20Status codes

A request has no credentials. Semantically, which response fits best?

Why: MDN: 401 semantically means unauthenticated, so the client must authenticate. 403 means the server knows who the client is and still refuses.
Question 6 of 20Status codes

A logged-in user requests an admin page they are not allowed to see. Which response is the usual fit?

Why: 403: the client does not have access rights and, unlike 401, the client's identity is known to the server.
Question 7 of 20Status codes

Which status code signals rate limiting, meaning too many requests in a given time?

Why: 429 Too Many Requests indicates the user has sent too many requests in a given amount of time.
Question 8 of 20Status codes

A server is down for maintenance and should tell clients to try again later. Which response fits?

Why: 503 is for temporary conditions such as maintenance or overload, and the Retry-After header should, if possible, give the estimated time to recovery.
Question 9 of 20JSON

Which of these is valid JSON?

Why: JSON requires double-quoted property names and strings, and trailing commas are forbidden. Comments and undefined are not supported.
Question 10 of 20JSON

What does JSON.parse throw when given malformed JSON?

Why: Running JSON.parse on invalid text such as {'a': 1} throws a SyntaxError, so wrap parsing of untrusted input in try/catch.
Question 11 of 20JSON

What does JSON.stringify({ a: undefined, b: 1 }) return?

Why: JSON has no undefined, and stringify leaves undefined-valued properties out of objects. Check the MDN JSON.stringify page for arrays and other cases.
Question 12 of 20Command line

In a POSIX shell, what does an exit code of 0 conventionally mean?

Why: Zero means success and a non-zero code means some kind of failure. Read the last exit code with $?, for example after grep -q.
Question 13 of 20Debugging

You are told a bug exists. What should you do first?

Why: A bug you can trigger on demand can be investigated, and a minimal case narrows the cause. Without reproduction you cannot tell whether a fix worked.
Question 14 of 20Debugging

Roughly how many checks does a binary search need to find the first bad version among 100 ordered versions?

Why: Each check halves the range, so 100 candidates need at most 7 checks. Tools such as git bisect use the same idea.
Question 15 of 20Testing

In Python's unittest, when does assertRaises(SomeError, ...) pass?

Why: The unittest docs: the test passes if the exception is raised, is an error if another exception is raised, and fails if no exception is raised.
Question 16 of 20Testing

When does unittest's setUp method run?

Why: setUp prepares the test fixture and is called immediately before calling each test method.
Question 17 of 20Security

What is the preferred defence against SQL injection according to OWASP?

Why: OWASP prefers parameterized queries. Concatenating untrusted values into a query before preparing it defeats this protection.
Question 18 of 20Security

A form checks every field in the browser. Do you still validate on the server?

Why: OWASP: validate on the server even when the browser checks the same fields. Client-side checks can be bypassed.
Question 19 of 20Security

An API key was committed to a repository. What should you do?

Why: OWASP advises rotating secrets regularly so stolen credentials only work for a short time. Once committed, history may still contain the key, so rotate it.
Question 20 of 20Security

What does least privilege mean for a secret or service account?

Why: OWASP: secrets must have the minimum privileges assigned to them to enable their required use or role.

Preparation checklist

  • Use a pipe, a redirect, an exit code and an environment variable in a shell
  • Say which HTTP methods are safe and idempotent, and choose a method for each action
  • Pick the right status code, including 401 versus 403 and 201 versus 200
  • Write valid JSON and handle malformed JSON in an API
  • Describe a debugging process: reproduce, shrink, hypothesise, bisect, fix, add a test
  • Write a unit test with normal, edge and error cases, and explain when to use a fake
  • Explain parameterized queries, server-side validation, and how you handle and rotate secrets
  • Check the linked official references for the version you use
